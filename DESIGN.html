HTTPS-Guard

An eBPF-based network security layer for OpenBMC: kernel-space probes observe TLS and HTTP traffic, a userspace daemon decides what to do about it, and the two halves feed back into each other.

§1 Overview

HTTPS-Guard detects TLS version downgrades and suspicious HTTP payloads on an OpenBMC device, then acts on what it sees — tearing down the offending TCP connection and blocking the source IP. It does this by splitting the work across a hard boundary: the kernel only observes, userspace only decides.

Two eBPF programs sit in the kernel. A uprobe on OpenSSL's SSL_write() is the primary sensor and works on every platform, including BMCs with no XDP support. An XDP program is an optional accelerator: where the NIC allows it, it inspects the TLS ClientHello at the wire and can drop known-bad traffic before it costs a single userspace round-trip.

Everything else — classifying an event, matching attack signatures, deciding to kill a connection — happens in a C++ daemon (https-guardd) that polls a shared ring buffer. This split matters for one concrete reason: an eBPF program is verifier-limited and cannot run arbitrary logic, while the daemon can use the full C++ standard library. Pushing intelligence to userspace is what lets the detector grow more sophisticated without ever touching the kernel program.

  • Hybrid enforcement — synchronous XDP_DROP for already-known offenders, asynchronous classification for everything new.
  • Learns forward — a threat the daemon catches asynchronously is written into the same BPF map XDP checks synchronously, so the next packet from that source is dropped in microseconds.
  • Degrades gracefully — on hardware without XDP (e.g. the AST2600 in SLIRP mode), the daemon falls back to uprobe-only reactive enforcement instead of failing.
  • Speaks Redfish — every decision is logged as a JSON event and bridged to D-Bus, the systemd journal, and bmcweb's EventService.

§2 Architecture

The diagram below is the whole system in one picture: two kernel probes feed a shared ring buffer, the daemon classifies what comes out of it, and three independent actions handle the response. The important detail is the loop at the right edge — BlocklistAddAction writes back into the exact BPF map that XDP's synchronous check reads, which is how an asynchronous detection becomes a synchronous defense for the next packet.

§3 Detect → Classify → Dispatch

The two kernel probes see different things and submit different structs — there is no shared "event" type, because the uprobe has no access to socket info and the XDP program has no access to the OpenSSL session. The daemon tells them apart by an event_source discriminator that is always the struct's first field.

Classification runs on DetectLoop's Boost.Asio loop, not in the ring-buffer callback — that callback only copies the record and posts it, because a slow callback lets the ring buffer fill and a full ring buffer silently drops events. Each rule is a pure function of one event:

detections/core/DetectLoop.cpp — simplified 
// Rules for this event source, in order; first match wins.
for (const auto& rule : detectors_[source]) {
    if (auto v = rule->evaluate(evt)) { verdict = *v; break; }
}
// No match: an inline "OK / traffic observed" verdict.

if (verdict.actionable) {
    evt.ensurePeerResolved();          // the /proc walk, only here
    if (evt.remote_ip_v4 != 0) {
        if (have_full_tuple) push(BlockTcpAction{...});
        push(BlocklistAddAction{evt.remote_ip_v4, ttl});
    }
}
push(LogAction{...});                  // always

Two properties of that loop are easy to lose in a rewrite and worth stating. Admission is bounded by an explicit in-flight count, because post() is an unbounded queue and on a ~1GB BMC an OOM — which takes all detection with it — is a far worse outcome than one dropped event; the policy is drop-the-newest, so what remains is a coherent prefix of history rather than a hole in the middle. And the loop runs two threads with the connection-rate sweep timer deliberately off the record strand: a single-threaded loop starves that timer by FIFO fairness alone, since it queues behind every record already posted. Measured against a deliberate backlog, one thread produced zero sweeps in nine seconds where two produced one every two.

A rule reaches hook-specific data through a capability interface rather than off a shared struct, so a certificate-access event is not obliged to carry a TLS version or a cipher-suite list. An event that cannot supply a capability is declined rather than misread.

A uprobe_event carries no socket info, so the 4-tuple is recovered from /proc — but lazily, only once a verdict is actionable, since that walk is the most expensive step in the pipeline and most events never reach it. It also fails closed: a process owning several established connections cannot be attributed to one, and enforcement declines rather than guessing. An xdp_event already has the tuple from the packet headers.

Why some rules enforce and others only alert. The blocklist applies to a source address on every port, so an actionable false positive removes all access to the BMC for the blocklist TTL. Cipher-suite and SNI findings describe an offer bmcweb refuses anyway, so alerting is proportionate — making them actionable locked an operator out of SSH during testing. The three per-source counting rules describe ongoing harm, so they enforce, which makes their thresholds safety-critical rather than tuning details.

§4 Class Relationships

The whole codebase plugs into three interfaces, and almost nothing else is polymorphic. IHookModule is a source of events, IDetector is a rule, IAction is a response. Adding a hook, a rule or a countermeasure means writing one class and adding one line to the composition root in programs/core/main.cpp — the engine classes are never touched.

That is the property worth protecting when reading the diagram below: HttpGuardProgram, DetectLoop and ActionLoop know only the interfaces. None of them names a concrete hook, rule or action.

The three seams
InterfaceContractImplemented byCalled from

IDetector evaluate(const hg_event&) const → optional<Verdict> 8 rules DetectLoop, first match wins per event source
IAction execute_async() → awaitable<void> 3 countermeasures ActionLoop, via co_spawn

IPeerResolver is the fourth seam and the odd one out: it exists so a uprobe event can recover its own 4-tuple from /proc on demand. That walk is the most expensive step in the pipeline and only the enforcing path needs it, so the event carries a non-owning pointer to the hook rather than the hook doing the work up front. SslUprobeProgram is therefore the one class implementing two seams at once.

The matrix is the point of the design, not a side effect of it. hg_event once carried 25 members covering every hook at once, so an LSM certificate-access event arrived holding a cipher-suite list and an SNI flag, and every new hook widened a type in the classification layer that every other hook depended on. Now a rule dynamic_casts to the one capability it needs and declines if the event cannot supply it — so the three sweeper-synthesised events can share a single hg_event_source and still not poach each other's work, because each carries only its own capability.

Two consequences are load-bearing. Events are non-copyable — copying one as an hg_event would slice off the hook's half — which is why parseEvent() returns unique_ptr<hg_event>. And ITlsTrafficInfo carries a tlsViolationHint() that exists purely to stop one specific bug: a genuinely parsed legacy_version of 0x0000 is a real violation on the wire, whereas tlsVersion() == 0 from a uprobe only means “never observed”. Collapsing those two zeros shipped once.

One structural rule holds all of this together, and breaking it is the easiest way to make the tree unbuildable: the dependency arrow points one way only.

library dependency direction 
actions_lib  <--  detections_lib  <--  programs_lib

IHookModule and hg_event therefore live in detections/core/ rather than in programs/, even though hooks implement them — putting them with the hooks would make the graph cyclic, since DetectLoop has to call hooks. For the same reason IHookModule.hpp forward-declares bpf_object and bpf_link instead of including <bpf/libbpf.h>: the classification tree must stay buildable, and unit-testable, with no kernel present. programs/ is the only tree that links libbpf, which is what stops a classification rule from acquiring a kernel dependency from the code sitting next to it.

§5 Two-Tier Security Model

These aren't two competing designs — they're two tiers of the same system, and the connection between them is the point. Tier 1 can only enforce what it already knows; Tier 2 is what teaches it something new.

Tradeoffs
AspectTier 1 — SynchronousTier 2 — Asynchronous
Policy complexityLow — eBPF verifier limitedUnlimited — full C++ stdlib

§6 Platform-Adaptive Enforcement

XDP requires a real netdev — SLIRP-mode QEMU and some real NICs don't offer one. Rather than treating that as a startup failure, the daemon attaches the uprobe unconditionally (it never fails) and treats XDP as optional, trying native attach first and falling back in order.

Verified platform support
PlatformNICUprobeXDP nativeXDP generic
ASpeed AST2600 (johnblue), bridge modeftgmac100✓✓*—
QEMU SLIRP (default)ftgmac100 (emulated)✓——
QEMU TAP+BRIDGEvirtio-net-*✓✓✓
x86_64 (native)ixgbe, mlx5, …✓✓✓

* Requires bridge mode — SLIRP gives the AST2600's ftgmac100 no real netdev to attach to.
